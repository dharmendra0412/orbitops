# ORBITOPS — Simulation Engine Specification

> **Authoritative-rule notice:** The later **Partial-hour execution contract** is final. Earlier full-hour battery/data shorthand and the earlier load-shedding order that lists survival/avionics loads as shed candidates are superseded and must not be implemented. The base bus/avionics are never shed; only heater demand above the survival minimum is shed.

## Authority, repeatability and fidelity

The backend owns all authoritative engineering validation, time histories, events and scoring. The completed engine result is a deterministic function of a canonical input snapshot, seed, engine version, ruleset version, score formula version and environment manifest. No wall clock, live network data, unseeded randomness, mutable catalog lookup or AI response may affect engineering calculations. An operational deadline may only produce technical `FAILED/SIMULATION_LIMIT` with null score/result, never a partial scored result. The only MVP PRNG is NumPy `Generator(PCG64)` with NumPy/runtime version pinned; derive independent streams from the documented SHA-256 stream seed so adding one subsystem does not reshuffle other event streams.

Canonical units: kg, W, Wh, seconds, m/s, decimal MB (`10^6` bytes), and credits. Do not mix byte and MB values in one field; convert at API/UI boundaries with explicit units. Use fixed time steps or discrete event times, never frame delta. Stable ordering is timestamp, event priority, event ID, then component ID. Input hashing uses `orbitops-cjson-v1`: normalized schema values serialized by the pinned Python backend as UTF-8 JSON with sorted keys/no insignificant whitespace, finite numbers only, negative zero normalized to zero, and the pinned runtime's shortest round-trip float representation; hash is SHA-256. Engine arithmetic uses IEEE-754 float64 in stable component/slot order and does not round between segments; presentation rounds only. Same pinned runtime/configuration must reproduce same ordered events and result hash. Runtime/platform upgrades may differ numerically; retain versioned old results and compare engineering outputs at declared tolerances instead of claiming cross-platform bitwise identity.

## Pipeline

1. Validate schemas and ranges; resolve all component IDs using pinned catalog.
2. Build immutable normalized mission state and record provenance references.
3. Calculate initial mass, power, energy, propulsion, data, communications and reliability budgets independently.
4. Evaluate mission constraints and emit named margins/violations.
5. Advance coarse mission timeline; apply illumination/environment schedule, operations duty cycles, charge/discharge, data generation/downlink, planned burns and seeded events.
6. Recompute affected budgets after events (e.g. degraded array, instrument failure) using same pure functions.
7. Produce summary, time series, ordered event log, constraint explanations and score breakdown.
8. Store complete input and result snapshots plus versions and hash.

## Independent engineering modules

| Module | MVP calculation |
|---|---|
| Mass | Sum component mass × quantity + explicitly modeled margin/propellant; report dry/wet mass distinctly. |
| Power | Array output = rated power × illumination factor × degradation factor; consumption = subsystem load × duty cycle. Clearly identify illustrative factors. |
| Energy | Battery state evolves by generated/consumed energy with capacity and charge/discharge efficiency and bounds. Detect brownout; no impossible energy creation. |
| Propulsion | Ideal rocket equation `Δv = Isp·g0·ln(m_initial/m_final)` for explicitly modeled propellant; do not infer vehicle performance from an invented hardware spec. Maneuver requirements are scenario game values unless sourced. |
| Data | Instrument generation = configured illustrative rate × operating time; storage occupancy adds generated and subtracts downlinked bytes. |
| Communications | Scheduled contact windows from scenario; delivered data capped by configured illustrative link rate × contact duration. Avoid claiming detailed link budget. |
| Reliability/events | Component failure hazard is a game-balance parameter by default; seeded event draw and documented hazard model; optionally expose reliability as illustrative mission success probability only. |
| Constraints | Compare margins to mission-defined limits: mass, power, energy reserve, data capacity, budget, delta-v, lifetime and required instrument capability. |

Its environment manifest contains exactly 720 outer-step entries for illumination factor, communication availability, display temperature, `heater_requested_w`, and `heater_survival_min_w`, plus sub-hour integer-second contact/operation schedules. Illumination and heater schedules are illustrative unless sourced and transformed with traceable provenance. ## Failure/event model

Keep deterministic planned events separate from stochastic game events. Event record includes `event_id`, sim time, type, affected component, severity, triggering probability/model ID and consequence. Events may disable instruments, reduce power, consume reserve or close a communication opportunity. Failure likelihoods must be visibly tagged `illustrative`, never represented as empirical hardware reliability absent a qualified source. Tests should verify seed repeatability, event stream isolation and state invariants.

## Scoring

Use a transparent rubric with named weighted dimensions: science objective completion, engineering feasibility, resource margin, budget discipline, data return and resilience. Each term defines bounded normalization and contribution. Hard constraint penalties are explicit; do not let score imply mission viability when a mandatory constraint fails. Weights and thresholds are ruleset/game-balancing values, versioned and disclosed. AI cannot propose or change score. Return per-objective evidence and a score formula version.

## Limitations

MVP does not claim high-fidelity orbit determination, terrain illumination prediction, thermal analysis, battery electrochemistry, radiation modeling, detailed communications link closure or real spacecraft reliability prediction. Planned maneuvers and contact windows are curated scenario inputs. These limits should appear in briefing and report.

## Final fixed-step equations and bounds

**Clock and initial state:** 30 days = `2,592,000 s`; `Δt=3,600 s`; exactly 720 surface steps from touchdown. `E_0=0.8C` Wh, data buffer `D_0=0 MB`, health factors `h_i=1`, all operations inactive until schedule says otherwise. 80% is illustrative. Transfer/descent are phase checks before surface steps. Units: kg, m/s, W, Wh, s, MB (decimal), credits.

**Mass:** `m_dry=Σ(m_i×quantity_i)` over every selected landed component exactly once, including bus and propulsion package; launcher is excluded. `m_payload=m_dry+m_propellant`; launcher cap requires `m_payload≤cap`, counting mission-level propellant exactly once. Launcher itself has zero landed mass. Dry/propellant/wet values are reported separately. Transfer/descent use this mass ledger and sequential delta-v checks; they do not advance a timed electrical-power or battery simulation. The descent package's 35 W is a catalog property for illustrative comparison, not a debit from the touchdown battery state.

**Budget/hard constraints:** `C_total=C_launcher+ΣC_selected`; proposed budget cap is 140 credits, illustrative. Feasibility hard gates are: exactly one launcher, launcher payload limit, transfer delta-v, descent delta-v, all mandatory subsystem categories, budget cap, and no loss of survival/avionics. Any pre-touchdown hard gate failure yields mission failure/score 0. Any mission-ending landed failure yields `mission_success=false` and score ≤49.9. A design may be structurally valid yet infeasible and run for educational diagnosis; malformed IDs, nonfinite/out-of-range inputs or missing immutable definitions are rejected before run.

**Power:** `P_solar(k)=P_rated × I_k × η × h`, where `I_k∈[0,1]` is cached site illumination factor, `η=0.85` illustrative, `h∈[0,1]`. `E_gen=P_solar×Δt/3600` Wh. `P_load=P_idle+ΣP_i×duty_i+P_heater+P_radio`, with W and duty in `[0,1]`.

**SUPERSEDED — do not implement this full-hour battery/load-shedding shorthand:** `E_raw=E_k+η_c max(E_gen−E_load,0)−max(E_load−E_gen,0)/η_d`; `η_c=η_d=0.95` illustrative. It applies one full-hour update and its older shed ordering included survival/avionics. Use only the later segment-level equation/dispatch contract: actual seconds, never shed avionics/base bus, and shed only heater demand above the survival minimum.

**SUPERSEDED — do not implement this full-hour data shorthand:** `D_(k+1)=D_k+G_k−U_k`. Use the later segment-level buffer rule: downlink only segment-start data, apply actual powered contact seconds, then add current-segment generation and evaluate overflow.

**Propulsion:** ideal rocket equation `Δv=Isp×9.80665×ln(m_before/m_after)` m/s, with Isp seconds and masses kg. Transfer requirement 700 m/s and descent 1,300 m/s are illustrative. Proposed demo descent package Isp 300 s and propellant 360 kg are illustrative, not NASA specs. Explicitly deduct propellant for transfer then descent. This is a budget check, not a trajectory or landing guidance model.

**Events:** pinned ruleset provides daily illustrative hazard probability `p_day`; step probability `p_step=1−(1−p_day)^(3600/86400)`. Seeded PRNG stream is derived by `(run_seed,event_subsystem_id)`. Apply event at step boundary; order simultaneous events by `(priority,event_id)`. Failure/event probabilities are not real reliability estimates.

**Deterministic event ruleset v1 (illustrative):** use NumPy `PCG64`, with NumPy version pinned in engine image. For each event stream, seed from the first 128 SHA-256 digest bits interpreted big-endian from UTF-8 string `orbitops-event-v1|{uint32_seed}|{stable_stream_id}`; draw uniforms in increasing step index and stable component ID. Candidate independent hazards per eligible installed subsystem: `RADIO_CONTACT_SKIP` daily p=.02 per radio, skips the next scheduled contact only; `INSTRUMENT_SAFE_MODE` daily p=.01 per instrument, disables it for 72 simulated hours; `ARRAY_OUTPUT_DEGRADE` daily p=.005 per array, permanently multiplies health by .90; `THERMAL_LOAD_SPIKE` daily p=.002 per thermal package, adds 20 W to requested heater power for the next three steps without raising the survival minimum. The thermal event may exceed component heater limit: actual electrical request is capped at the installed `heater_power_limit_w`, and the difference is recorded as `heater_capacity_shortfall_w`; this excess is above the survival minimum and creates no fictitious draw. It is not independently terminal because MVP has no thermal state, but event/resilience reporting records it. All probabilities and impacts are illustrative. Events are drawn at beginning of step after scheduled degradation; one event can affect each subsystem per step, and eligible events are all applied in priority then stable event ID order. No failure probability is presented as flight reliability. The mission-ending base-bus/survival rules are deterministic consequences of energy availability, not random event labels.

**Validation:** finite numbers only; nonnegative mass, cost, power draw, data rates, capacities; efficiencies/fractions `[0,1]`; Isp and step positive; exactly 30 days and 3,600 s for this ruleset; integer quantities within limits; all schedules cover 720 steps; contact/illumination fractions `[0,1]`. Invalid schema rejects run; infeasible constraints can execute and return failure. Pin Python/NumPy/PRNG and canonical serialization. Promise exact event order and same-runtime result hash; across runtime/platform upgrades use numeric tolerances and retain old results, rather than claiming universal bit-identical floats.

**SUPERSEDED — full-hour battery shorthand (do not implement):** For each one-hour step calculate `E_gen=P_solar(W)×3600/3600` Wh and requested load `E_req=P_req(W)×3600/3600` Wh. First shed scheduled loads only as needed, producing `E_shed`; dispatch load is `E_dispatch=E_req−E_shed`. Set `surplus=max(E_gen−E_dispatch,0)` and `deficit=max(E_dispatch−E_gen,0)`. With illustrative `η_c=η_d=.95`: for surplus, `candidate=E_k+η_c×surplus`; for deficit, `candidate=E_k−deficit/η_d`; then `E_(k+1)=clip(candidate,0,C)`. Battery-delivered energy is `min(deficit,η_d×E_k)`. Electrical unserved is `max(0,deficit−η_d×E_k)`. Actual consumed energy is `E_dispatch−E_unserved`; requested, shed, consumed and unserved are distinct report metrics. For surplus, wasted energy is `surplus−max(0,E_(k+1)−E_k)` (conversion loss plus capacity clipping); otherwise wasted is zero. All are Wh. Do not count shed energy a second time as electrical unserved. Use the actual-segment-seconds contract below.

**SUPERSEDED — full-hour load-shedding shorthand:** If forecast depletion requires shedding, recompute demand after dropping loads in this exact order: (1) noncritical science duty, (2) camera observations, (3) high-rate radio, (4) low-rate radio, (5) heater demand above survival minimum. Never shed avionics/base bus. Brownout is any shed load or unserved energy. The earlier two-step thermal-failure wording is also superseded: MVP does not integrate a temperature state, so it must not claim a separate temperature-based failure. The later partial-hour dispatch and failure policy is authoritative.

### Propulsion sequence and mass ledger

Use one abstract propulsion package/budget for transfer and descent at the same illustrative `Isp=300 s`. No separate engine and no duplicate propellant. `m_dry` includes bus, mounted hardware and propulsion hardware, excludes usable propellant. `m0=m_dry+m_p0` is initial wet payload; compare it once to launcher payload capacity. For each burn in order, target `m_after=m_before/exp(Δv_req/(Isp×9.80665))`; propellant consumed is `m_before−m_after`. If available propellant is less, use all remaining propellant, calculate achieved Δv=`Isp×g0×ln(m_before/m_after_actual)`, flag phase failure, stop later phases and do not land. Final landed mass is `m_dry+m_residual_propellant`.

Illustrative feasible vector (independent mass fixture, not the minimum-cost catalog design): `m_dry=295 kg`, propellant 360 kg, `m0=655 kg`; transfer 700 m/s leaves 516.3069 kg (138.6931 kg consumed); descent 1,300 m/s leaves 331.8969 kg (184.4100 kg consumed); residual 36.8969 kg; landed mass 331.8969 kg. `Isp×g0=2,941.995 m/s`; total available is about 2,346.7 m/s, above 2,000 m/s required. Insufficient vector: same dry mass, only 180 kg propellant; transfer leaves 374.4211 kg after consuming 100.5789 kg; remaining 79.4211 kg can provide about 701.4 m/s of descent, below 1,300 m/s. Flag `DESCENT_PROPELLANT_SHORTFALL`, no surface run. Rounded values may differ by 0.1 kg; compute full precision. All requirements are illustrative, not NASA specifications.

### Fully specified score terms

Evaluate once at mission completion/terminal failure. Every ratio clips `n/d` to `[0,1]`; zero denominator yields 0 plus `undefined_denominator`. Missing required telemetry fails the run, never imputes success. Selected required objectives form objective denominator; optional objectives are excluded. `S=round(100×(.30A+.25F+.15E+.15R+.15O),1)`.

All opportunity and operation denominators are derived from the complete pinned 30-day schedule, not just steps reached; after terminal failure, future scheduled items count incomplete and future critical load counts unserved. A technically interrupted/invalid run (e.g. missing required engine output or backend restart) has `score=null` and terminal infrastructure failure, not a mission score. This differs from a simulated mission-ending event, which has a valid partial mission score subject to the 49.9 cap.

- `A=.45×(distinct required objectives with ≥1 valid observation / selected required objectives) + .35×(valid scheduled observations completed / valid scheduled observations) + .20×(science MB successfully downlinked / expected science MB in the complete pinned 30-day schedule)`. The expected-data denominator is precomputed from all selected-instrument scheduled activations in the frozen design: continuous instruments use configured MB/h × full scheduled duty-active seconds / 3600; camera uses 2 MB × all scheduled observations. It is fixed before simulation and is not reduced by early terminal failure, shedding, degradation, safe mode or missed opportunities. Thus early failure cannot improve this ratio by shrinking generated-data denominator. No selected required objectives, no valid opportunities, or expected data of zero yields 0 for the corresponding term and an explanatory flag. Cap all ratios at 1.

At run acceptance, compute `expected_science_data_mb` from the exact pinned design/catalog/operation schedule before the engine task starts and store it in the immutable `input_snapshot`; also store it in final score evidence. A zero denominator is stored as zero with `undefined_denominator`; it is not inferred later from observed run output.
- `F=1` iff every pre-touchdown hard gate passes: launcher payload, transfer, descent, mandatory categories, budget and survival; otherwise 0. Any pre-touchdown hard-gate failure yields overall score exactly 0, as specified below.
- `E=.40×payload_margin_norm + .30×energy_reserve_norm + .30×budget_remaining_norm`. Normalize as `clip((cap−m0)/(.10×cap),0,1)`, `clip(minimum_step_end_battery/(.15×installed_capacity),0,1)`, and `clip((budget−spent)/(.10×budget),0,1)`. Targets 10%, 15%, 10% are illustrative. Zero denominator yields 0.
- `R=.50×(steps with survival and avionics served/720) + .30×(critical-load Wh served/critical-load Wh requested) + .20×(recoverable events restored within next 24 steps/recoverable events)`. No recoverable events yields 1 for the final term with explanation; zero critical demand yields 0.
- `O=.35×(observations completed/scheduled observations)+.30×(contacts completed/scheduled contacts)+.20×(steps without storage overflow/720)+.15×(non-science operations completed/scheduled non-science operations)`. Zero scheduled opportunities yields 0 with explanation.

For `O`, an observation is completed only if its full scheduled interval executes with the instrument powered and its complete expected payload stored; a contact is completed only if the scheduled radio is powered for the entire required interval and attempts a data transfer (zero available data still counts as an attempted contact, but yields zero downlink). Non-science operations are the versioned survival/housekeeping schedule; completion requires its required load served. Each scheduled item is counted once, not once per substep.

Pre-touchdown infeasibility scores exactly 0. Mission-ending landed failure caps calculated score at 49.9. Successful missions can score 0–100. Examples: success `(A,F,E,R,O)=(.8,1,.7,.9,.8)` → 85.0; landed failure `(.6,1,.4,.5,.5)` raw 64.0 → capped score 49.9; perfect success `(1,1,1,1,1)` →100.0; any pre-touchdown infeasibility→0. Early-failure denominator vector: selected objectives 2 with 1 achieved, 8 scheduled observations with 2 completed, and expected science data 100 MB with 20 MB downlinked gives `A=.45×.5+.35×.25+.20×.20=.3525`. With other pinned terms `(F,E,R,O)=(1,.5,.25,.25)`, raw score is `100×(.30×.3525+.25+.15×.5+.15×.25+.15×.25)=50.575`, so landed-failure cap yields 49.9. The partial numerator must never produce a 100% data-return ratio by reducing the fixed 100 MB denominator. A pre-touchdown failed hard gate remains exactly 0.

`mission_success=true` only when all pre-touchdown hard gates pass and all 720 landed steps complete without a mission-ending condition. A hard gate failure before touchdown is score 0. A terminal surface failure before step 720 produces a valid partial mission score capped at 49.9. Infrastructure/engine failure has no score (`null`), as defined above.

The denominator correction is `score_formula_version=lander-score-v2`; pin this identifier in every run snapshot/result and report. `lander-score-v1` is superseded and must not be used for new runs. Example denominator tests (illustrative): complete schedule expects 100 MB and successfully downlinks 80 MB, so science data return = `.80`; if mission terminates early after only 20 MB was generated and downlinked, the denominator remains 100 MB and ratio = `.20`, not 1.0. A successful full run with expected 100 MB and 100 MB downlinked yields 1.0. These ratios feed only the `.20` science-data-return subterm of A; early failure also incurs the existing score cap and incomplete-operation penalties.

### Exact step order and output boundaries

### Partial-hour execution contract

The one-hour outer step remains 3,600 seconds but is split at every scheduled operation/contact start and end, observation completion, and mode change. Schedule intervals are integer-second half-open `[start_offset_s,end_offset_s)` ranges within a step. Calculate exact overlap seconds. Illumination and temperature use the pinned hourly environmental average.

For each duty-cycled operation with factor `d∈[0,1]`, derive active duration as `floor(d×eligible_interval_seconds)` and activate at the start of that eligible interval; evaluate each interval separately. Add the derived active-end second as a segment boundary. For the selected thermal package, compute `P_H_req=environment.heater_requested_w×heater_load_multiplier` and `P_H_min=environment.heater_survival_min_w×heater_load_multiplier`; these are exact scheduled electrical loads with no hidden clipping. Preflight checks `P_H_req≤heater_power_limit_w` and `P_H_min≤P_H_req` for all 720 entries; violation is schema-valid physical infeasibility (`SURVIVAL_HEATER_CAPACITY`), producing pre-touchdown mission failure and score 0 rather than rejecting the run. `THERMAL_LOAD_SPIKE` is the documented exception: add 20 W to requested heater draw, cap actual request at the component limit and report the excess as capacity shortfall. Heater energies are actual W draw times powered active seconds / 3600. Instrument and radio energy equals `power_draw_w×powered_active_seconds/3600 Wh`. Solar energy is `rated_power_w×illumination×efficiency×health×segment_seconds/3600 Wh`. Contacts deliver at `downlink_rate_mb_per_s×actual_powered_contact_seconds`. Battery efficiency and clipping are applied at every segment boundary using the segment's actual seconds. No operation is charged a full hour unless it actually runs the full hour.

#### Authoritative segment battery dispatch mathematics

For every segment let `t_s` be its positive integer duration in seconds; `E_k` the beginning battery stored energy in Wh; `C` its capacity in Wh; `P_solar` the segment's constant effective solar power in W; and `η_c,η_d∈(0,1]` the pinned charge/discharge efficiencies (both `.95` in the illustrative ruleset). Require `0≤E_k≤C`; `C=0` is valid and means storage is disabled. For each active subsystem `i`, `E_req,i=P_i(W)×t_i(s)/3600` Wh, where `t_i` is its scheduled active overlap; scheduled intervals are clipped to the segment. Sum all active subsystem energies, including base bus/avionics, heater and radio, to obtain `E_req`. Solar energy is `G=P_solar(W)×t_s(s)/3600` Wh. All arithmetic uses decimal/float64 canonical order: stable component ID order, then stable slot order; no rounding between segments. Round only displayed report values. Clamp only within a documented numeric tolerance of `1e-12 Wh`; a larger bound violation is an engine error.

Let `H_req` be scheduled heater energy and `H_min` the survival-minimum heater energy for the same segment, with `0≤H_min≤H_req`. First compute deliverable battery energy `B_avail=η_d×E_k` Wh and total available bus energy `A=G+B_avail`. The only permitted curtailment is `H_excess=max(0,H_req−H_min)`. If `E_req>A`, curtail `H_shed=min(H_excess,E_req−A)`, then set `E_req2=E_req−H_shed`; otherwise `H_shed=0` and `E_req2=E_req`. This minimizes heater curtailment while leaving every other scheduled load untouched. Record heater shed Wh and degraded-power telemetry. There is no protected reserve cutoff.

Dispatch after curtailment uses the following exhaustive branches. Set `E_load=E_req2`.

1. **Surplus or exactly balanced (`G≥E_load`):** actual consumed energy `E_consumed=E_load`; battery discharge `B_delivered=0`; surplus `S=G−E_load`. Battery input accepted for charging is `S_acc=min(S,(C−E_k)/η_c)` when `C>0`, otherwise zero. Stored increase `ΔE=η_c×S_acc`; `E_(k+1)=E_k+ΔE`; charge conversion loss `L_c=S_acc−ΔE`; capacity-clipping/unused solar `W_cap=S−S_acc`; total wasted solar `W=S−ΔE=L_c+W_cap`. Thus energy from the array either serves loads, is stored, or is reported as loss/unused; clipping never raises battery energy above `C`.
2. **Deficit (`G<E_load`):** `D=E_load−G`; battery-delivered energy `B_delivered=min(D,B_avail)`; internal battery withdrawal `B_withdrawn=B_delivered/η_d`; `E_(k+1)=E_k−B_withdrawn`; actual energy absorbed at the bus `E_consumed=G+B_delivered`; discharge loss `L_d=B_withdrawn−B_delivered`; `W=0`; and `E_unserved=D−B_delivered`. Treat a residual at or below `1e-12 Wh` as zero; a larger positive residual after heater curtailment terminates immediately with `POWER_BROWNOUT`. During that terminal segment the partial bus energy is counted as consumed/aborted load energy, but no operation is considered fully powered or credited: powered-active seconds and generated/downlinked data for its operations are zero. Retain calculated supply, consumption, battery and unserved metrics; do not continue to later segments. This is the explicit coarse-step failure convention; it conserves energy without fabricating science or contact completion.

For `C=0`, `B_avail=0` and `S_acc=0`; generation may serve contemporaneous loads, but surplus is wasted and any positive deficit is unserved. For `G=0`, the deficit branch applies directly. If `E_k=0` as well, battery contribution is zero. Energy conservation in a charging segment is `G=E_consumed+ΔE+L_c+W_cap`. In a deficit segment the bus balance is `G+B_delivered=E_consumed`; the battery state balance is `E_k=E_(k+1)+B_withdrawn`, and `B_withdrawn=B_delivered+L_d`. Separately, requested-load accounting is `E_load=E_consumed+E_unserved`. Do not add unserved demand to supplied energy; it is demand that was never supplied. Validate these identities to `1e-9 Wh` in golden tests. `E_(k+1)` is always clipped only for floating-point tolerance, never to hide a physical overdraw.

(g) unserved after allowed curtailment: same state/duration, other loads 30 W→7.5 Wh and heater 20 W→5 Wh including 2 Wh minimum; demand 12.5 Wh, shed all 3 Wh excess, remaining 9.5 Wh equals available supply so no unserved. Increase other loads to 32 W→8 Wh: remaining demand 10 Wh, supply 9.5 Wh, end 0, unserved .5 Wh and immediate terminal `POWER_BROWNOUT`; other loads are never shed.

Camera observations are discrete scheduled 60-second intervals (illustrative) and generate exactly 2 MB once at completion only if powered through the entire interval; otherwise they are missed with no data generated. They do not also accrue a continuous MB/h rate. Continuous instrument generation is `(rate_mb_per_h/3600)×powered_active_seconds`. For a powered contact, `U=min(D_start,downlink_rate_mb_per_s×actual_powered_contact_seconds)`; with no powered contact, `U=0`. For causality, a segment downlinks only data already in the buffer at segment start; that segment's generated data becomes eligible at the next segment. Update `D_pre=D_start−U+G`, `D_next=min(C_data,D_pre)`, and overflow `max(0,D_pre−C_data)` after downlink. Data uses decimal MB. Since `U≤D_start` and only eligible `G` is counted, cumulative downlinked science data cannot exceed cumulative generated data; storage overflow is discarded and never downlinked later.

Observation accounting distinguishes operation completion from valid science return. Each scheduled opportunity has a stable `observation_id`, instrument, interval and expected generated payload. A camera payload is atomic 2 MB; it is generated only after its full 60 s powered exposure. Continuous-instrument opportunity payload is configured rate × actual scheduled powered-active seconds. Generated data `G` is counted even if later overflowed, but storage admission is bounded by free decimal MB. Credit a valid science observation/objective only when the entire opportunity ran and its full payload was stored; otherwise mark it invalid for science achievement (and record overflow as applicable). An instrument may continue its scheduled operation while data overflows, but lost bytes never count toward science return. This distinguishes sensed activity, stored observation evidence and downlinked data.

Load shedding triggers under the equations above when requested energy exceeds solar energy plus battery deliverable energy. The sole shed candidate is heater demand above the survival minimum. Never shed instruments, camera, radios, base bus or avionics. If unserved energy remains, terminate immediately with `POWER_BROWNOUT`; apply the failed-segment accounting and no-operation-credit behavior defined above. If the unserved quantity includes required survival-minimum heater energy, set secondary failure cause `THERMAL_SURVIVAL_UNPOWERED`; the terminal execution status remains `FAILED` only for an engine/infrastructure error, while this simulated mission event yields `COMPLETED`, `mission_success=false` and a numeric capped score. A scheduled camera observation is complete only if its entire 60-second interval is powered; otherwise it is missed and generates no data. A contact is complete only if its entire scheduled contact interval is powered; otherwise it is incomplete. For any fully powered contact, downlink capacity is rate × actual powered contact seconds and is further capped by segment-start stored data. Heater curtailment alone is nonterminal degraded-power telemetry. This policy intentionally does not allow science or communications to be independently interrupted while the mission continues. MVP has no temperature state equation or separate temperature-based terminal failure; survival is represented by the explicitly scheduled minimum heater energy and its power availability, not a claim of thermal analysis.

The base bus and avionics are never shed under any condition. Heater load below or equal to the survival minimum is also never shed; only heater demand above that floor is eligible for curtailment.

Only heater excess is curtailed for the current segment; it may resume at the next segment if still scheduled and energy-feasible. Science, camera and radio are never shed to preserve another load. If energy cannot support the scheduled non-heater loads plus survival-floor heat, the terminal brownout occurs in that segment under the failed-segment accounting rule above; the segment's operations receive no credit, camera observations are missed, and contacts are incomplete. An instrument disabled by an event does not resume until the event-defined recovery time.

This partial-hour contract supersedes the earlier full-step shorthand for power/data operations.

The partial-hour execution contract above defines the authoritative step order; it replaces this section's earlier shorthand ordering. Score accumulators still close once per outer step, and exactly 720 outer steps are run unless a terminal mission failure occurs.

Store per outer step aggregate Wh for solar generation, actual bus energy consumed, unserved load, battery stored energy, charge/discharge conversion losses, unused/capacity-clipped solar, and heater energy curtailed; store MB for data buffer/generation/downlink/overflow, credited powered-active seconds, completed/missed observations, contact completion, active/shed flags and event IDs. ## Applied scoring consistency correction (2026-11-12)

`F` measures **pre-touchdown hard-gate feasibility only**. If all launcher, payload, transfer, descent, mandatory-subsystem, budget and survival gates passed before touchdown, `F=1` remains true even if a later landed-operations failure occurs. A landed failure is handled by `mission_success=false` and the overall score cap of 49.9; it does not retroactively change pre-touchdown feasibility to zero. The landed-failure worked example is therefore `(.6,1,.4,.5,.5)`, raw score 64.0, final capped score 49.9. Pre-touchdown infeasibility still scores exactly 0.
