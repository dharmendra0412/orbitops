# ORBITOPS — Database Schema

PostgreSQL is the durable source of truth. Use UUID primary keys, UTC `timestamptz`, foreign keys, checks, and indexes. Store canonical units in column names or documented JSON schemas. Enable RLS for user-facing tables. API backend uses a restricted database role; migrations are version-controlled. Use JSONB for immutable versioned snapshots/results, not as a substitute for all relational structure.

## Tables

| `missions` | `id`, `scenario_id`, `scenario_version`, `owner_id` FK to profile with deletion restricted until ownership transfer, `member_count INT NOT NULL DEFAULT 0 CHECK (member_count BETWEEN 0 AND 4)`, `title`, `status`, `current_revision_no`, `room_sequence`, `created_at`, `updated_at`. Status constrained to `draft, active, archived`; sequence/revision start at 0. |
| `mission_members` | `(mission_id,user_id)` PK, `role` in `owner, editor, viewer`, `joined_at`; `mission_id → missions(id) ON DELETE CASCADE` only for an otherwise deletable empty mission; `user_id → profiles(user_id) ON DELETE RESTRICT`; room membership authorization. |
| `mission_invitations` | `id`, `mission_id`, `created_by`, `role CHECK IN ('editor','viewer')`, `token_hash BYTEA UNIQUE`, `token_key_version`, `created_at`, second-precision `expires_at`, `accepted_by`, `accepted_at`, `revoked_at`; mission FK `ON DELETE RESTRICT`, creator/acceptor profile FKs `ON DELETE SET NULL`. | `component_definitions` | `(catalog_version, component_id)` PK, `category`, `name`, `model_json`, `provenance_json`, `limits_json`, `is_available`; FK `catalog_version → catalog_versions(version) ON DELETE RESTRICT`. Canonical catalog snapshot. |

Composite FK `(mission_id,design_revision_id) → design_revisions(mission_id,id)` enforces same-mission revision; composite FK `(mission_id,design_revision_id,catalog_version) → design_revisions(mission_id,id,catalog_version)` ensures run uses that revision's catalog. Direct FKs to `catalog_versions(version)` and `environment_manifests(id)` prevent dangling versions. Add `UNIQUE(mission_id,id)` for mission-scoped receipt/event FKs. State checks: RUNNING has null `completed_at`, `mission_success`, `failure_code`, `result_json`, `result_hash`, and score; COMPLETED has `completed_at`, `result_json`, result hash, nonnull mission success and score, null `failure_code`; FAILED has `completed_at`, null mission success/score/result JSON/result hash, and nonnull technical `failure_code`. A simulated failure code such as `POWER_BROWNOUT` lives in `result_json.mission_failure_code`, leaves run `failure_code` null, and still yields COMPLETED/numeric score. ## Design snapshot shape

The code block is a schema example; `south_pole_site_a` is a placeholder ID, not an approved named lunar site or NASA dataset.

```json
{
  "schema_version": "1",
  "catalog_version": "lander-mvp-1",
  "mission_profile": {"duration_days": 30, "site_id": "south_pole_site_a"},
  "components": [{"slot": "power.primary", "component_id": "solar_fixed_80", "quantity": 1}],
  "operations": {"instrument_duty_cycle": 0.25, "downlink_policy": "scheduled"}
}
```

The catalog IDs are resolved against pinned catalog version `lander-mvp-1`; the example ID `solar_fixed_80` exists in that catalog. Do not embed editable physical properties in a draft. `input_snapshot` for a run includes fully resolved component values and exact environment/ruleset/engine/score-formula versions so future catalog edits cannot change past runs.

## Relationships and retention

Mission owns many members, revisions and runs. Revisions reference parent revisions and are append-only. Runs reference exactly one revision and one version of each input. Deleting a user should follow an account retention policy; preserve anonymized run artifacts only if policy permits. Keep high-volume presence out of Postgres. Apply retention limits to transient room events and failed-run diagnostics.

For invitation creation, the `api_idempotency.resource_id` points to `mission_invitations.id`; its saved `response_json` omits the bearer token and stores only nonsecret response fields. On an exact retry within 24 hours, the backend derives the identical token from the invitation ID, stored expiry/key version and retained HMAC key, then reconstructs the original response. Neither invitation rows, receipts, request logs nor diagnostics store the plaintext token.

## RLS and access patterns

Members can read a mission if membership exists. Owners/editors may create revisions and request runs; viewers may read. Only backend policies/service may publish catalogs, mutate run results, or ingest data manifests. Validate every backend request independently of RLS. Index memberships by `user_id`, revisions by `(mission_id,revision_no DESC)`, runs by `(mission_id,started_at DESC)`, simulation events by `(run_id,sequence_no)`, room events by `(mission_id,sequence_no)`, and manifests by `(source_name,retrieved_at DESC)`.

## Referential integrity, indexes, deletion and immutability

- `design_revisions`: `UNIQUE(mission_id,id)` supports composite FKs; `UNIQUE(mission_id,revision_no)` rejects duplicate numbers even under concurrent inserts. `FOREIGN KEY(mission_id,parent_revision_id) REFERENCES design_revisions(mission_id,id) ON DELETE RESTRICT` guarantees parent mission matches; root revision has null parent, self-parent is rejected, and a trigger requires parent `revision_no < NEW.revision_no`. `FOREIGN KEY(catalog_version) REFERENCES catalog_versions(version) ON DELETE RESTRICT` prevents dangling catalog versions. Allocate the next number by locking the mission row or compare-and-swap on `current_revision_no` in the same transaction that inserts the revision and advances the pointer; the unique constraint is the final race guard.
- `simulation_runs`: composite FKs `(mission_id,design_revision_id) REFERENCES design_revisions(mission_id,id) ON DELETE RESTRICT` and `(mission_id,design_revision_id,catalog_version) REFERENCES design_revisions(mission_id,id,catalog_version) ON DELETE RESTRICT`; direct FKs `catalog_version → catalog_versions(version)` and `environment_manifest_id → environment_manifests(id)`, also `ON DELETE RESTRICT`. A run cannot pair another mission's revision or a different catalog from its revision. Keep `score_formula_version` explicit and immutable.
- `catalog_versions.source_manifest_id`, `environment_manifests.data_manifest_id → data_manifests.id ON DELETE RESTRICT`; component definitions reference catalog version with `ON DELETE RESTRICT`. Catalog/environment/data versions are never hard deleted while referenced. All `simulation_runs.environment_manifest_id` values must be nonnull and reference an immutable environment manifest; deployments requiring an explicitly illustrative environment still seed a real versioned illustrative manifest instead of using null or bypassing the FK.
- `missions.member_count` is maintained only by `AFTER INSERT/DELETE` triggers on `mission_members`; insert atomically increments only where count `<4`, otherwise raises and rolls back; delete decrements. Its check enforces 0–4. Serialize membership/invitation acceptance by locking the mission row before count/insert. A partial unique index allows at most one `role='owner'`; a deferred constraint trigger requires that `missions.owner_id` is its owner-role member at commit, so initial creation and ownership transfer can be atomic. `mission_invitations` token hash is unique, mission deletion is restricted while invitations exist, and invitation updates permit only one `accepted_at/accepted_by` or `revoked_at` transition; identity/token/expiry/role fields are immutable. Acceptance locks the mission row, validates token and expiry, and commits invitation use, membership and idempotency receipt together; capacity failure rolls back without consuming the invitation.
- Indexes: unique `(mission_id,revision_no)` and `(mission_id,id)` on revisions; `(mission_id,created_at DESC)` on revisions and `(mission_id,started_at DESC)` on runs; partial unique `simulation_runs(mission_id) WHERE status='RUNNING'`; `room_events(mission_id,sequence_no)` unique and `(created_at)` for retention purge; `room_commands(mission_id,command_id)` PK; REST idempotency unique scope and `(created_at)`; `run_diagnostics(expires_at)`; `environment_manifests(site_id,version)` unique; unique `mission_invitations(token_hash)` plus `(mission_id,created_by,created_at DESC)` for invite rate limits; source manifest lookup `(source_name,retrieved_at DESC)`. Add indexes on FK columns where not covered by composite indexes; specifically index reverse-reference columns if the referenced-key prefix does not cover deletion checks.
- Revisions, data manifests and environment manifests are append-only: runtime role has INSERT/SELECT only where needed; `BEFORE UPDATE OR DELETE` triggers reject mutation. Published catalog versions and their component definitions are immutable: a catalog-version trigger allows draft→published only if version/content hash/source/ruleset are unchanged and publication time is set; it rejects later update/delete. Component triggers reject insert/update/delete whenever the parent is published; draft rows may change only while the parent remains draft. Run input snapshot, mission/revision/catalog/environment/engine/rules/execution-profile/score versions, seed and initial request hash cannot change after creation. A `BEFORE UPDATE OR DELETE` run trigger permits only one transition from `RUNNING` to `COMPLETED` or `FAILED`, with immutable identity/input fields; it rejects any update/delete once old status is terminal. Add a separate `CHECK` enforcing each row's status/nullability/result shape, including required/null result hash. A CHECK alone does not enforce transition history. Backend runtime role is not table owner and cannot disable triggers, truncate, bypass RLS, or mutate immutable tables directly; retain terminal rows while the mission is retained.
- Do not hard-delete missions with revisions, runs, invitations, commands or events; archive missions. Foreign keys to mission history use `RESTRICT`. Membership can be removed; historical actor references use `ON DELETE SET NULL` where identity erasure is required. Mission ownership must be transferred before profile removal. Purge API idempotency receipts after 24 hours; purge redacted `run_diagnostics` after 30 days while retaining run row/snapshot/failure code per mission retention. WebSocket command receipts remain for mission/run retention. Room event rows may be purged after 7 days only; retain room sequence and reconstruct current recovery snapshot from mission, current revision and latest run in one consistent DB snapshot.

Reconnect never depends on unbounded event history. If `last_seen_sequence < oldest_retained_sequence−1`, exceeds captured current sequence, or any gap is found, return a full current snapshot with a captured `room_sequence`; if no events remain but cursor differs from current sequence, also use snapshot fallback. Snapshot includes mission role, current immutable revision, run states and current sequence. Subscribe to the process-local mission queue first and buffer live frames, then read consistent snapshot/replay and captured sequence in one repeatable-read transaction; discard buffered events at/below snapshot sequence and merge remaining events in sequence order. This closes the commit-between-snapshot-and-subscribe gap without new infrastructure. A commit whose broadcast is interrupted by process failure remains in durable event history and is replayed on reconnect. Client deduplicates by sequence and requests resync on gaps.

## Migration and consistency decisions

Use SQL migrations and seed a versioned catalog. Create `profiles` and `data_manifests` before `catalog_versions` and `environment_manifests`, then component definitions, revisions and runs; add late composite FKs/triggers after referenced tables exist. Migration owner is a separate non-login role; runtime role cannot own tables, disable triggers, truncate immutable data or bypass RLS. Create revisions with `expected_revision_no` compare-and-swap and unique `(mission_id,revision_no)` in the same transaction. Increment room sequence and insert its event in the same transaction so rollback leaves neither. Create a run with its command receipt, immutable snapshot and first event transactionally before execution. If acquisition or transaction fails before commit, roll back all writes and release semaphore. If execution fails after acceptance, persist `FAILED` and diagnostic; process death is handled by startup recovery. Persist final result and terminal state atomically. FastAPI WebSockets broadcast only after committed database changes; PostgreSQL remains the synchronization record.

## Final MVP consistency changes

Remove Supabase Realtime from synchronization. FastAPI writes revisions, room sequence and run state directly to Postgres. Add `room_commands(mission_id, command_id, actor_id, command_type, request_hash, outcome_json, created_at)` with composite primary key for socket command idempotency. Each mission has monotonic `room_sequence`; increment and insert durable event in the same transaction. Design revisions use compare-and-swap expected revision and immutable inserts. Launcher choice, 30-day duration, 3,600-second time step, site/environment version, transfer/descent parameters and schedules are included in immutable run input. Store seed as uint32 and pin engine/ruleset/catalog/environment versions. Keep ephemeral presence in FastAPI memory and rebuild from reconnect snapshot. In-process per-mission locks help serialize one instance, but database uniqueness and optimistic checks remain correctness mechanisms. No broker or worker schema is needed for MVP.

## Consistency contract additions

Add `missions.current_revision_no` (or equivalent compare-and-swap column) and `missions.room_sequence BIGINT NOT NULL DEFAULT 0`. `room_commands` primary key is `(mission_id,command_id)` and stores SHA-256 request hash plus serialized original acceptance outcome so exact retries return the same run ID; key reuse with changed payload is rejected. Retain these receipts for mission/run retention lifetime. `room_events` contains only durable events with `(mission_id,sequence_no)` unique and is retained for 7 days; when cursor is older, return current snapshot instead of incomplete replay. Presence remains in memory only. Concurrent run starts use the partial unique index `UNIQUE(mission_id) WHERE status='RUNNING'`, in addition to the one-instance global semaphore. Before opening the WebSocket listener or accepting API work on startup, atomically mark every pre-existing `RUNNING` row `FAILED`, set `failure_code=BACKEND_RESTARTED`, `completed_at=now()`, `mission_success=NULL`, and leave `score/result_json` null; add a redacted diagnostic record. Do not resume a partial run. The exact accepted command remains idempotent and returns its original run/outcome; a deliberate retry uses a new command ID and a valid current revision.

The immutable run snapshot includes normalized 18-item catalog records, launcher selection and payload cap, mission-level propellant exactly once, dry mass inputs, 30-day/3,600-second schedule, precomputed `expected_science_data_mb`, engine/ruleset/execution-profile/environment/catalog/score-formula versions, budget and seed. The science denominator is calculated before execution from the complete pinned schedule. The catalog provenance/unit schema is defined in [COMPONENT_CATALOG_SPEC.md](COMPONENT_CATALOG_SPEC.md). Supabase Auth identity is not a substitute for `mission_members`; enforce RLS and the same role rules in FastAPI. The single-instance in-process semaphore allows one simulation globally; a busy start is rejected with `429 SIMULATION_BUSY`, not stored in an unbounded queue. The per-mission active-run uniqueness constraint remains a defensive invariant.

**SUPERSEDED ordering shorthand:** for a new `run_start`, after idempotency lookup and semaphore acquisition, one transaction creates the run receipt/row and ordered `run_status` event. Completion transaction stores result/hash/status and terminal event before broadcast. Use the corrected duplicate/busy order immediately below; receipt lookup precedes semaphore acquisition.

**Corrected duplicate/busy order (supersedes the preceding sentence's semaphore-first wording):** authenticate and authorize, acquire the per-command in-process lock, and look up `(mission_id,command_id)` receipt plus canonical request hash first. Equal existing hash returns the stored outcome/run ID regardless of semaphore state; unequal hash returns `409 IDEMPOTENCY_KEY_REUSED`. Only a genuinely new key attempts a nonblocking global semaphore. Busy returns `429 SIMULATION_BUSY` without inserting receipt or run. After semaphore acquisition, one Postgres transaction inserts the unique command receipt, immutable run snapshot and `RUNNING` row plus first room event. If two new duplicate requests race past lookup, the unique-key loser releases any acquired semaphore, reads the committed receipt and returns the same result/hash conflict. The same canonical `run_start` JSON schema in API_SPECIFICATION.md is used; the backend checks mission ownership, referenced revision number and current revision number before snapshotting.

Run state constraint is `RUNNING → COMPLETED | FAILED`; no `QUEUED` state. `COMPLETED` is an engine-complete report even when `mission_success=false`; `FAILED` is technical termination and has `score=null` plus a failure code. Both are terminal. Mission phase (`DESIGN, TRANSFER, DESCENT, LANDED_OPERATIONS, COMPLETE, FAILED`) is stored separately. REST idempotency receipts and WebSocket command receipts use separate tables/namespaces, with same-hash replay and changed-hash conflict semantics as documented in the API contract. Presence is excluded from all tables/receipts/sequences.


## Applied consistency correction (2026-11-12)

`simulation_runs.seed` is `BIGINT`, not PostgreSQL `INT`, because the API accepts the complete unsigned 32-bit range `0..4,294,967,295`. The CHECK constraint enforces that range. The implementation migration and tests must use the same type and bounds.
